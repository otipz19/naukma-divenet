# Design

## Context

See proposal.md for motivation. ADR-0006 and the Media section of `docs/ARCHITECTURE.md`
fix the outline: `POST /api/v1/media`, JPEG/PNG/WebP up to 10 MB checked by content,
`MediaStorage` on local disk, a thumbnail on upload, files served from `/media/{id}` and
`/media/{id}/thumb`, and cleanup of unreferenced uploads after 24 h.

Already in place: `frontend/nginx.conf` proxies `/media/` and sets `client_max_body_size 10m`;
the SPA fallback skips `/media/` (spec `shared/local-stack`); `.gitignore` ignores `media-data/`.
Not in place: no `media` package, no scheduling, no multipart limits, no media volume in
`compose.yaml`, no `/media` proxy in `vite.config.ts`. `SecurityConfig` permits anonymous GET
only under `/api/v1/**`. The JDK's ImageIO reads JPEG and PNG but not WebP.

## Goals / Non-Goals

**Goals:**

- One upload path and one lifecycle (upload → attach → release or expire) that
  `add-site-reviews`, `add-diver-profile` and `add-posts` reuse unchanged.
- Bounded memory and disk use per upload, whatever the client sends.

**Non-Goals:**

- Join tables between media and content. Each consuming change adds its own
  (`review_media`, ...) and calls `attach` / `release`.
- A list or delete endpoint for one's own uploads. Removing a photo from a form only drops it
  from the form; the cleanup deletes it if nothing attaches it.
- Image editing, cropping, EXIF handling, more than one thumbnail size.

## Decisions

### D1: Schema

`V6__create_media.sql`:

```sql
media (
  id uuid PK,                                  -- random, generated by the service
  uploader_id bigint NOT NULL REFERENCES users,
  content_type varchar(16) NOT NULL CHECK (IN ('image/jpeg','image/png','image/webp')),
  size_bytes bigint NOT NULL CHECK (> 0),
  width integer NOT NULL CHECK (> 0),
  height integer NOT NULL CHECK (> 0),
  created_at timestamptz NOT NULL,
  attached_at timestamptz                      -- null until a feature attaches it
)
-- partial index for the cleanup
CREATE INDEX media_unattached_created_at ON media (created_at) WHERE attached_at IS NULL;
```

A random UUID keeps unattached uploads private in practice: they are served publicly
(D2), but nobody can guess their URL. `attached_at` replaces a reference count: consumers
attach once and release once, so a flag is enough. `Media` maps `@ManyToOne User`.

### D2: Endpoints

| Endpoint | Access | Response |
| --- | --- | --- |
| `POST /api/v1/media` (multipart, part `file`) | authenticated | 201, `Location: /media/{id}`, `{ id, url, thumbnailUrl, contentType, width, height }` |
| `GET /media/{id}` | anonymous | 200, the stored bytes, stored content type |
| `GET /media/{id}/thumb` | anonymous | 200, `image/jpeg` |

`MediaController` (upload) and `MediaFileController` (files) live in `media.web`. The file
routes are outside `/api/v1`, so springdoc's `paths-to-match` keeps them out of
`api/openapi.json`; they serve bytes, not JSON. Both file responses send
`Cache-Control: public, max-age=31536000, immutable` and `Content-Disposition: inline`;
Spring Security already adds `X-Content-Type-Options: nosniff`. The path variable is a
`String` parsed as a UUID, so a malformed id gives 404 rather than a 400 type-mismatch.
`SecurityConfig` adds `GET /media/**` to the anonymous rules.

Errors, all problem details:

| Case | Status | Source |
| --- | --- | --- |
| No `file` part | 400, `errors: [{field: "file"}]` | `GlobalExceptionHandler` overrides `handleMissingServletRequestPart` to add `errors` |
| Over 10 MB | 413 | `MaxUploadSizeExceededException`, handled by `ResponseEntityExceptionHandler` |
| Not JPEG/PNG/WebP by content | 415 | `UnsupportedImageException` (`ErrorResponseException`) |
| Undecodable, or over 50 MP | 400 | `InvalidImageException` |
| Unknown media | 404 | `MediaNotFoundException` |

`application.yaml`: `spring.servlet.multipart.max-file-size: 10MB`, `max-request-size: 11MB`,
and `server.tomcat.max-swallow-size: 12MB`, so Tomcat reads the rest of a too-large request and
the client gets the 413 body instead of a reset connection. `docs/ARCHITECTURE.md` gets 413 and
415 in its list of status codes.

### D3: Storage

`MediaStorage` (in `media.service`): `void write(String key, byte[] bytes)`,
`Optional<Resource> read(String key)`, `void delete(String key)`. `LocalDiskMediaStorage`
implements it under `divenet.media.dir` (`${MEDIA_DIR:media-data}`; tests use a temporary
directory). Keys are `{id}` and `{id}.thumb.jpg`, stored under a two-character subfolder (the
id's first two hex digits), so no folder grows past a few hundred files. A write goes to a
temporary file in the same folder and is then moved into place atomically, so a reader never
sees a half-written file.

Order of work and what happens on failure:

- **Upload:** validate and decode (D4), write both files, then insert the row. If the insert's
  transaction rolls back, a `TransactionSynchronization` deletes the two files.
- **Release and cleanup:** delete the rows in the transaction, and delete the files after the
  commit. A file left behind by a crash has no row, so it is never served; that leak is accepted.

### D4: Validation and thumbnails

1. The type comes from the first 12 bytes: `FF D8 FF` JPEG, `89 50 4E 47 0D 0A 1A 0A` PNG,
   `RIFF....WEBP` WebP. Anything else gives 415. The file name and declared content type are
   ignored.
2. An `ImageReader` for that format reads the width and height from the header. Above 50 million
   pixels gives 400, before any pixels are decoded.
3. The reader decodes with source subsampling chosen so the decoded image is at most twice the
   thumbnail size. A decode error gives 400. Memory per upload stays at a few megabytes, even for
   a 50 MP image.
4. The thumbnail is scaled with bicubic interpolation to a longer side of
   `min(640, longer side)` (rounded), drawn on white, and written as JPEG at quality 0.85.

The original is stored byte for byte, without being re-encoded. WebP reading comes from
`com.twelvemonkeys.imageio:imageio-webp`, which registers an ImageIO reader through SPI. Its
version is pinned in `backend/pom.xml` properties, like the other non-Boot versions.

### D5: Attach and release

`MediaService` is the API for other features:

- `List<MediaView> attach(Collection<UUID> ids, long userId)`: one
  `UPDATE media SET attached_at = :now WHERE id IN (:ids) AND uploader_id = :user AND attached_at IS NULL`.
  If fewer rows change than ids given, the transaction rolls back and
  `MediaNotAttachableException` (400, detail naming the first refused id) is thrown. The single
  update also makes attach and the cleanup safe against each other: an upload the cleanup deleted
  first is simply refused.
- `void release(Collection<UUID> ids)`: deletes the rows, then the files after commit (D3).

Both join the caller's transaction, so a review that fails to save attaches nothing. They are
tested here through `MediaServiceIT`, because no feature calls them yet.

### D6: Cleanup

`SchedulingConfig` in `shared.config` adds `@EnableScheduling`. `MediaCleanup` (in
`media.service`) runs with `fixedDelayString = "${divenet.media.cleanup-interval:PT1H}"` and an
initial delay of 5 minutes. It runs `DELETE FROM media WHERE attached_at IS NULL AND created_at < :cutoff RETURNING id`,
with the cutoff 24 hours before `Clock` time, and deletes the files after commit. Tests call it
directly with a fixed `Clock`. The app is single-node (ADR-0006), so no lock is needed.

### D7: Front-end upload and `PhotoField`

- `src/api/media.ts`: `uploadMedia(file: File)` calls `api.POST("/api/v1/media", ...)` with a
  `bodySerializer` that builds `FormData`, so it goes through `authFetch` (bearer token,
  refresh and retry) and fails with `ApiError` like every other call.
- `components/PhotoField` is controlled: `value: UploadedMedia[]`, `onChange`, `max`, and an
  optional `label`. It fits React Hook Form's `Controller`. Each picked file gets a slot in pick
  order; uploads run in parallel, and each finished upload fills its slot, so the order holds
  whatever finishes first.
- Checks before upload: size over 10 MB, or `file.type` not one of the three types. The server
  checks again by content.
- `ApiError` status to message: 413 too large, 415 wrong type, 400 unreadable, anything else
  or no response "try again".
- Layout from `ReviewForm.html`: 3:2 tiles of `--space-8` height with `--radius-sm` and
  `object-fit: cover`, the busy placeholder on `--surface-2`, and the secondary `Button` for "Add
  photo". The real `<input type="file">` is visually hidden and opened by the button.
- i18n namespace `media.photoField` (label, add, hint, hintLimit, alt, remove, uploading,
  errors.*, skipped), in `en` and `uk`.

No page uses the field yet. Tests render it directly with MSW, and the browser check uses a
harness that is not committed (tasks 5.3).

### D8: Stack

- `compose.yaml`: the back-end gets `MEDIA_DIR: /data/media` and the named volume
  `media-data:/data/media`. The value is fixed, so `.env.example` does not change.
- `backend/Dockerfile` creates `/data/media` owned by the `divenet` user, so a new named volume
  takes that ownership and the app can write to it.
- `frontend/nginx.conf`: `client_max_body_size 11m` (10 MB file plus multipart framing).
- `vite.config.ts` proxies `/media` like `/api`.
- `scripts/compose-rules.mjs` checks that the back-end's `/data/media` is on a named volume.
- `scripts/smoke-stack.mjs` registers a user, uploads a JPEG padded to exactly 10 MiB through
  the web port (JPEG decoders stop at the end-of-image marker), checks `/media/{id}` and
  `/thumb`, and checks both again after the restart it already does.

### New or changed interfaces (summary)

- **Endpoints:** `POST /api/v1/media`; `GET /media/{id}`; `GET /media/{id}/thumb`.
- **Migrations:** `V6__create_media.sql`.
- **i18n namespaces:** `media.photoField`.
- **Configuration:** `divenet.media.dir` (`MEDIA_DIR`), `divenet.media.cleanup-interval`, the multipart
  and swallow limits.

## Risks / Trade-offs

- **EXIF orientation:** phone JPEGs that are rotated only by EXIF show upright as originals in
  browsers, but their thumbnails come out sideways. Accepted for now; if the demo needs it, a
  later change reads the orientation tag in D4 step 4.
- **EXIF privacy:** originals keep their metadata, including any GPS position. For photos of
  public dive sites this is acceptable; stripping it would mean re-encoding originals.
- **Public unattached uploads:** anyone with the URL can fetch an upload before it is attached.
  The URL is a random UUID, and the upload expires within about 25 hours unless it is attached.
- **No quota:** a signed-in user can fill the disk with uploads. Each upload is capped, and the
  unattached ones expire, which is enough for a demo.
- **Problem detail on an image route:** a 404 at `/media/...` returns `application/problem+json`.
  Browsers send `Accept: */*` with image requests, so the problem detail is acceptable to them.
